# Atlas for Android

Native Android frontend for [LMS147/atlas-agent](https://github.com/LMS147/atlas-agent), inspired by the supplied Atlas screen reference.

## Run

1. Extract this project and open `android` in Android Studio.
2. Use JDK 17 and install Android SDK 35 through SDK Manager.
3. Sync Gradle, then run `app` on an Android 8.0+ emulator or device.
4. Tap **Explore demo**. No credentials or backend are required for the preview.

Command line, with the SDK configured in `local.properties` or `ANDROID_HOME`:

```sh
./gradlew testDebugUnitTest assembleDebug
```

Windows:

```powershell
.\gradlew.bat testDebugUnitTest assembleDebug
```

The debug APK will be at `app/build/outputs/apk/debug/app-debug.apk`.
Pinned toolchain: Gradle 8.11.1, Android Gradle Plugin 8.9.2, Kotlin/Compose compiler 2.1.20, Compose BOM 2025.04.01. These are deliberate fixed versions, not claims of the latest versions.

## Included

- Welcome and server setup screens; demo mode with explicit labels.
- Material 3 dark theme, blue/cyan branding, navigation drawer, quick actions.
- Live authenticated HTTPS chat with the FastAPI/Groq backend.

- Gradle wrapper and API URL validation unit tests.

## Backend connection

Android v0.5.1 pre-fills `https://atlas-api-a9s1.onrender.com` when no server is selected. The address stays editable and saved server choices are preserved. Enter your private `ATLAS_API_TOKEN` in Server setup; no token or Groq key is built into the APK.

The monorepo backend implements [the API contract](../docs/api.md). Configure backend/.env with a Groq key and a separate ATLAS_API_TOKEN, start `python -m backend.app` from the root, and expose it through an HTTPS tunnel. Enter the tunnel URL and Atlas token on the connection screen. See [setup](../docs/setup.md).

Demo replies remain deterministic local examples. Live chat invokes the existing Groq agent, server histories persist in SQLite, and memory remains Markdown/GitHub-backed. Workspace files support upload/download and UTF-8 editing; the profile stays read-only. Memory management, available hardware metrics and conversation persistence use the authenticated server API. Attaching files to AI messages and executing commands remain future work.

## Data and credentials

The app asks for an **Atlas access token**, not the Groq key. The Groq key must stay in the server environment. The token is attached only to requests sent to the configured server; HTTPS is required, redirects and automatic connection retries are disabled. Only connect to a server you trust. Cloudflare Access service-token headers are not implemented; use an HTTPS tunnel forwarding to the backend, which validates the Atlas bearer token.

Remembered URL/token pairs are encrypted with an AES-GCM key generated by Android Keystore. Backup is disabled. Tokens are not saved in Room or logs. Cache rows are separated by server and token identity; demo data has its own scope. Room chat/memory content is ordinary app-private SQLite, not an encrypted database. Disconnect removes saved credentials but retains caches; clear local chat removes only the current workspace's messages. This does not reset the server session. Timestamp preference is kept during the current app process only.

## Real chat and recovery

1. Start your configured API and HTTPS tunnel as described in ../docs/setup.md.
2. Enter the HTTPS server URL and Atlas access token on Server setup. The app checks authenticated health before switching workspaces.
3. Send a message (maximum 8,000 characters). The user message is saved before the request, and the actual server reply is cached after success.
4. If the connection drops, choose **Check for reply** on that message. The app reads its status using the original UUID and conversation ID. A saved result is restored without posting another inference request. If no record exists yet, **Retry delivery…** asks before sending the original UUID again. It does not retry automatically.
5. Explicit backend failures show **Send again…**, which asks for confirmation before creating a new request UUID. The previous request may have saved a memory before failing; inspect the conversation/memory first.

Pending sends are converted to recoverable messages when reconnecting after an app restart. Check for an unresolved reply before composing the next turn. Cached failure state survives restarts. Retrying a completed send is a no-op; replies have deterministic local IDs so recovery does not create duplicate bubbles. Network failures never become demo responses.

Room schema version 3 groups messages into persistent conversations, after the version-2 delivery migration; both upgrade paths preserve existing chat and memory. It does not destructively reset existing chat or memory. In-place Android updates require the same signing key; keep your original signing key when upgrading an installed debug build. A differently signed APK cannot perform that in-place update. The database is still app-private SQLite. Clearing local chat still does not reset the server conversation.

## Saved conversations

Open **History** or the **Conversations** menu to start, select, rename, or delete chats. Android v0.3 uses the server-generated ID on every message. Complete transcripts live on the backend; Room caches downloaded pages and remembers the active chat. **Load earlier messages** downloads the next older page without resetting model context or duplicating cached bubbles.

Older single-chat caches are grouped under their original `android-<workspace>` ID so server context continues. Existing demo messages move into `demo-main`. A server refresh merges completed messages by request ID, including a reply that arrived after your connection dropped. Unfinished attempts remain recoverable locally. A fresh installation can download completed history from the server; pending local drafts/failure state are not a server transcript.

During network outages, a previously cached workspace can open its local chats. A chat missing from the server is retained as a read-only cached copy; an explicit deletion tombstone removes it on sync. New server conversations require a working API connection. Demo chats remain device-only. Deleting a chat does not delete shared memory facts.

Tests cover cross-chat isolation, selected-chat restoration, history reconstruction with an empty client cache, pagination, tombstones, read-only missing-history caches, offline startup, delivery recovery, and both Room upgrade paths.

## Reliability v0.4

Recovery uses GET request status, not chat POST. Pending requests remain recoverable; interrupted/failed requests require a confirmed new UUID. Unknown deliveries get a separate confirmation that reuses the original UUID. The composer waits for an unresolved delivery to be checked or resolved. Rate-limit errors show the server's Retry-After delay. require_existing=true prevents a new client from recreating a missing server conversation with empty context. The existing Room schema remains version 3; the additional delivery state is stored in the existing text column.

Update the backend to v0.4 before using this app version. The backend also provides supervised Termux startup, crash recovery, logs, and boot-hook installation; see deployment/termux/README.md from the repository root.
